## 3. Replay

- [x] 3.1 `replayRecording()` in `@vinto/engine` (`replay.ts`) with divergence reporting; unit tests for faithful replay, hash mismatch, rejected action, unknown version. Comparison is by canonical hash, not deep equality: replay reconstructs engine state only, and `turnActions`/`roundActions` are client-written, so a replayed state legitimately has no history
- [x] 3.2 `tools/replay-recording.ts` CLI (file or directory, PASS/FAIL lines, divergence report file, non-zero exit). Run via `npm run recordings:replay -- <path> [--report <file>]`. Verified: passes clean recordings with exit 0, and on a corrupted hash prints the divergence, keeps checking the rest, writes the report and exits 1. An empty directory is a failure, not a pass — "nothing was checked" must not read as "everything replays"
- [x] 3.3 `tools/generate-recordings.ts` (seeded headless self-play via `BotAIAdapter` with `skipDelays`, always 4 players, hashes filled in). Run via `npm run recordings:generate -- --games N --seed S`. Resolved the runner gap by adding `vite-node` (same family as the vitest already in use); the packages' `exports` point at `.ts` source, which `ts-node` cannot load through `node_modules` workspace symlinks. A `@vinto/local-client/headless` subpath export was added so CLIs get `GameClient`/`BotAIAdapter`/`initializeGame` without pulling in React
  - Two things learned while building it, both encoded in the tool: the `BotAIAdapter` must be constructed **before** leaving `setup`, because it drives bots from a MobX reaction and the `FINISH_SETUP` dispatch is what kicks it off; and `FINISH_SETUP` is a single global phase transition, not per-player, so only one dispatch is needed and the rest are correctly rejected
  - **RESOLVED — bots now call Vinto.** Originally all-bot self-play ran indefinitely (68 turns / 17 rounds, hands at 1,1,1,2, `vintoCallerId` still `null`). Root cause: `BotAIAdapter` only asks `shouldCallVinto` during the toss-in window (`botAIAdapter.ts:763`), which makes `constructGameState` set `isTossInPhase` (`mcts-bot-decision.ts:744`), and `MCTSMoveGenerator.generateMoves` returns only `pass`/`toss-in` in that branch (`mcts-move-generator.ts:73-111`) — so the `call-vinto` move was unreachable and the "did MCTS suggest Vinto?" gate failed 100% of the time. Replaced by a direct rule in `packages/bot/src/lib/vinto-call-rule.ts`: call when the hand is fully known and worth ≤ 0. Self-play now reaches `scoring` in ~250–370 actions, with `CALL_VINTO`, a `vintoCallerId` and a `coalitionLeaderId`, so the corpus can cover final scoring and the coalition round
  - **Generator capture bug, found by the parity gate on the first real corpus and now fixed.** One fixture in 50 failed to replay with a `hash-mismatch` on `DECLARE_KING_ACTION`. It was not an engine defect: replay proved deterministic across runs and every earlier action hashed identically, so the engine had produced the same state both times — the _recording_ had stored the wrong one. Cause: the generator snapshotted `client.state` after `dispatch()` returned, but `dispatch` is a MobX `@action`, so reactions fire as it completes and the `BotAIAdapter` can dispatch re-entrantly; by the time the snapshot ran, `client.state` had moved on. (An earlier deep-copy-at-capture change reduced but did not eliminate this — copying the wrong state faithfully still yields the wrong state.) `GameRecorder` now stores the state each action produced, captured inside `dispatch` before any observer can react, and `GameClient.exportRecordingWithHashes()` derives hashes from those, so actions and hashes are aligned by construction
- [~] 3.4 **Retired with `legacy-web/`.** Scenario fixtures were to be exported from the TypeScript scenario tests; the generator goes when that tree does (§1d). The corpus that exists — 50 recordings, 13,900 actions — is frozen and still gates the Kotlin engine. What this task was for is now served by 6.7 in `migrate-to-kotlin-multiplatform`, which generates fresh recordings from the *Kotlin* engine
- [x] 3.5 Commit initial corpus: 50 seeded self-play recordings in `fixtures/recordings/`, all replaying cleanly with a `stateHash` on every action. Coverage is asserted by the parity suite rather than assumed: 22+ games reach `scoring`, 25+ contain a coalition final round, at least one has a mid-game draw-pile reshuffle (the engine's only consumer of `rngState`), and all of DRAW_CARD / DISCARD_CARD / USE_CARD_ACTION / SELECT_ACTION_TARGET / PARTICIPATE_IN_TOSS_IN / DECLARE_KING_ACTION / CALL_VINTO appear. `fixtures/** -text` in `.gitattributes` keeps the committed bytes exactly as generated
  - **Prerequisite — do not commit the corpus before the state model is frozen.** Phase 1 of change `migrate-to-kotlin-multiplatform` (bot tournament → delete the losing bot → remove `botVersion`) mutates `GameState` (`packages/shapes/src/lib/game-state-types.ts:48`), so every canonical hash changes when it lands. Committing ≥ 50 fixtures first guarantees regenerating all of them and sets a bad precedent for fixture governance in the very first corpus commit. Tasks 3.1–3.4 and all of phase 2 may proceed in parallel with that work; only this commit blocks on it.
- [x] 3.6 Vitest parity suite in `packages/engine` replaying every fixture; add to `nx test engine`. Verified in both directions: it replays a real generated fixture green, and fails with a readable divergence report (action index, reason, both hashes) when a hash is corrupted. While the corpus is absent it skips with a stated reason rather than passing vacuously, and once the directory exists it asserts the corpus is non-empty and that every recorded action carries a state hash
